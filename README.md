# butschster/tui-desktop

Оконный менеджер для терминала на рантайме Wippy.

Один процесс-композитор владеет физическим экраном и рисует окна; каждое окно —
отдельный процесс, который пишет в собственный viewport через обычный `tty` и
считает, что владеет терминалом целиком. Ни одно окно не знает, что оно окно:
поэтому в окне работает настоящий `bash`, `htop`, редактор или Claude Code —
без единой строчки, написанной под этот десктоп.

Тем же экраном одновременно управляет агент: у модуля есть HTTP-канал, которым
можно открыть окно, переставить его, напечатать в него и **прочитать его экран**.

```
физический TTY → surface композитора → viewport → процесс окна → PTY-прокси → программа
```

## Что нужно

- Wippy **0.3.40a** или новее — модуль `tty` появился там (#631, фиксы в #637).
- Приложение Kickside, дающее `app:api` (роутер с аутентификацией).

## Запуск

```bash
wippy run --host butschster.tui_desktop:terminal desktop
```

`--host` здесь обязателен, и это не придирка: автодетект терминального хоста в
CLI — просто подсчёт записей `terminal.host` во всём реестре, а этот модуль
приносит вторую. С момента установки **каждая** команда приложения требует
явного `--host`; соседние команды выбирают хост приложения
(`--host wippy.terminal:host`).

Собственный хост нужен ради `hide_logs`. Диффер поверхности считает себя
единственным писателем в терминал, поэтому строка лога разъезжает кадр
насовсем — неизменившиеся строки не перерисовываются. Забрать под это хост
приложения нельзя: на нём живут фоновые процессы, и приложение лишилось бы лога.

### Клавиши

- `alt+n` — новое окно с интерактивным bash
- `alt+o` — меню окон, которые объявило приложение
- `alt+w` — закрыть текущее окно
- `alt+m` — свернуть текущее окно
- `alt+tab` — следующее окно
- `alt+1`…`alt+9` — окно по номеру из полосы сверху
- `ctrl+q` — закрыть все окна и выйти

Всё остальное уходит внутрь окна. Акселераторы держатся на `alt` нарочно:
`ctrl` и `tab` слишком часто нужны самим программам, и красть их — значит
ломать редактор внутри.

Мышью можно перетащить окно за заголовок, потянуть за правый нижний угол,
нажать `[-]`, `[□]`, `[×]` и переключиться по вкладке сверху. Включённая мышь
забирает у терминала обычное выделение текста — для копирования держите Shift.

## Командный канал

Все ручки живут за аутентифицированным роутером приложения.

- `GET /tui-desktop/windows` — открытые окна, фокус, размер экрана
- `POST /tui-desktop/windows` — открыть окно: `entry`, `command`, `title`, `x`, `y`, `w`, `h`
- `POST /tui-desktop/windows/{id}/type` — напечатать `text`, при `enter: true` с переводом строки
- `POST /tui-desktop/windows/{id}/key` — одна клавиша: `key`, `ctrl`, `alt`, `shift`
- `POST /tui-desktop/windows/{id}/screen` — содержимое окна строками
- `POST /tui-desktop/windows/{id}/move` — переставить: `x`, `y`
- `POST /tui-desktop/windows/{id}/resize` — размер: `w`, `h`
- `POST /tui-desktop/windows/{id}/focus` — поднять наверх
- `POST /tui-desktop/windows/{id}/minimize` — свернуть или развернуть: `value`
- `POST /tui-desktop/windows/{id}/close` — закрыть

Мастерская — окна, собранные на ходу:

- `POST /tui-desktop/apps` — собрать окно: `name`, `source`, `title`, `width`, `height`, `modules`
- `GET /tui-desktop/apps` — сохранённые окна и признак `live` (есть ли запись в реестре сейчас)
- `DELETE /tui-desktop/apps/{name}` — убрать окно из хранилища и реестра

Префикс пути задаёт роутер приложения, а не модуль: `/api/v1` на стенде
kickside, `/api` в харнессе. Промах отдаёт страницу фасада с кодом 200, поэтому
проверять стоит по `content-type`, а не по коду.

```bash
curl -X POST -H 'Content-Type: application/json' \
  -d '{"title":"сборка","command":"/bin/bash --noprofile --norc"}' \
  http://localhost:8099/api/v1/tui-desktop/windows

curl -X POST -H 'Content-Type: application/json' \
  -d '{"text":"make test","enter":true}' \
  http://localhost:8099/api/v1/tui-desktop/windows/w1/type

curl -X POST -H 'Content-Type: application/json' -d '{}' \
  http://localhost:8099/api/v1/tui-desktop/windows/w1/screen
```

Команды без ответа не бывает: молчание композитора невозможно отличить от
применённой команды, и вызывающий поверил бы в успех. Незапущенный десктоп и
неотвечающий десктоп — тоже разные ответы.

## Окна приносит приложение

Модуль знает ровно одно своё окно — программу под PTY. Всё остальное объявляет
приложение записью процесса, которая умеет писать в свой `tty`-порт; пометка
`meta.type: tui_desktop.window` кладёт её в меню `alt+o`, а `meta.title`,
`meta.width` и `meta.height` говорят, как её открыть. Ни строчки в этом модуле
править для нового окна не нужно — иначе каждое приложение требовало бы релиза
десктопа.

Ещё два поля описывают, чем окно является и где его искать:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `meta.window_type` | `app` | `app`, `dialog` или `tool` — по нему тема выбирает состав кнопок заголовка |
| `meta.in_menu` | `true` | `false` прячет программу из «Пуска», не мешая открыть её ярлыком или из другого окна |

- **Неизвестный тип — это `app` и предупреждение в лог**, а не спрятанная
  программа: запись объявил кто-то другой, и опечатка в одном поле не повод не
  показать окно, которое в остальном исправно.
- **Признак, а не вывод из типа.** Диалог в меню не нужен почти никогда, но
  «почти» тут дорого стоит: «О программе» — диалог, и его место как раз в меню.
- **Прячется меню, а не запуск.** `in_menu: false` не мешает ни ярлыку на
  столе, ни `desktop.open` из соседнего окна, ни командному каналу.

```yaml
- name: window_calc
  kind: process.lua
  meta:
    type: tui_desktop.window
    title: Калькулятор
    width: 28
    height: 15
  source: file://window_calc.lua
  method: main
  modules: [channel, tty]
```

Такое окно открывает поверхность своего порта и публикует кадры — в отличие от
окна с программой, где аренду порта забирает себе PTY-сессия. Через командный
канал оно открывается по имени записи: `{"entry": "app.desktop:window_calc"}`.

## Окно можно собрать в работающем рантайме

Реестр меняется на живую (`snapshot → changes → apply`), поэтому окно не обязано
быть файлом: его код едет в теле запроса, и окно появляется в меню сразу — без
перезапуска.

```bash
curl -X POST -H 'Content-Type: application/json' \
  -d '{"name":"clock","title":"Часы","width":30,"height":6,
       "modules":["time"],"source":"…lua…"}' \
  http://localhost:8099/api/v1/tui-desktop/apps
```

Исходник при этом ложится в таблицу `butschster_tui_desktop_windows`, и на
старте композитор возвращает сохранённые окна в реестр. Без этого собранное
окно жило бы ровно до конца процесса.

Восстанавливает именно композитор, а не фоновый сервис, и это не выбор стиля:
платформа намеренно запрещает процессам группы `wippy.security:process` менять
реестр — политика `wippy.security:registry.no_write` перекрывает разрешения
явным `deny`, и такой сервис молча не делал бы ничего. Композитор работает под
собственным актором, а нужны эти окна ровно тогда, когда десктоп запущен.

Итог восстановления виден снаружи — `GET /tui-desktop/windows` отдаёт поле
`restore` (`restored`, `failed`, `names`, `error`). Лог терминального хоста
заглушён, иначе он разъедет кадр, поэтому отказ, рассказанный только в лог, не
рассказан никому.

- **Одна строка на окно, имя — ключ.** Повторная сборка перезаписывает: история
  правок не ведётся, а «имя занято» было бы отказом чинить собственное окно.
- **Сборка окна одна на оба пути.** Мастерская и загрузчик строят запись одним
  и тем же кодом — разойдись они, окно вело бы себя по-разному до и после
  перезапуска, а такое расхождение проявляется через сутки.
- **Модули окна выбираются из белого списка**: `channel`, `time`, `tty`,
  `json`, `sql`, `env`; `tty` и `channel` добавляются всегда. Запрошенный
  модуль вне списка — отказ с его именем, а не молчаливое игнорирование.
  Порождать процессы и запускать программы окну нечем: код приходит по HTTP,
  и права выданы ровно под рисование и чтение данных.
- **Библиотека получает СВОИ модули, а не модули окна.** Список у записи окна
  ограничивает код самого окна; библиотека, которую окно импортирует, работает
  со списком, объявленным у неё. Поэтому `desktop` читает имя композитора
  модулем `ctx`, которого в белом списке окна нет, и ни одно существующее окно
  править не пришлось. Комментарий в `apps.lua` про «библиотеке нужен process»
  читается наоборот — он про удобство самого окна, а не про требование
  библиотеки. Доказательство лежит тестом: `app:window_probe_bare` объявляет
  только `process` и всё равно получает имя.
- **Удаление не гасит открытые окна.** Процесс живёт своей жизнью; удалена
  возможность открыть новое, и ответ говорит об этом прямо.

## Окно может попросить десктоп

Клики и клавиши доезжают до окна как есть — композитор транслирует их в его
координаты. Обратный путь даёт библиотека `desktop`, которую мастерская
подключает каждому собранному окну:

```lua
local desktop = require("desktop")

desktop.open({entry = "…:dataflow_detail", title = "Узлы", args = flow_id, w = 86, h = 18})
desktop.focus(id)
desktop.close(id)
```

Так виджет становится действующим: клик по строке открывает соседнее окно с
параметром. Окно-приложение получает свой параметр как `args`; `command`
остаётся программой для PTY-окна — одно поле на оба смысла читалось бы как
«команда», и окно подробностей открывали бы строкой `/bin/bash`.

Граница при этом узкая и проверяется тестом: окно умеет **попросить**
(`process.send` и найти адресата), но `spawn`, `exec` и `registry.apply` ему не
выданы. Присланный по HTTP код может дёргать ровно те команды десктопа, что и
так открыты снаружи, — и ничего сверх.

Ответа `desktop.open` не ждёт намеренно: ожидание чужого ответа заморозило бы
кадр окна, а что окно открылось, видно на экране. Когда ответ всё-таки нужен —
`desktop.open_wait` (то же самое, но с описанием открытого окна, включая `id`),
`desktop.ask` и `desktop.replies()`, см. ниже: они не читают inbox и потому не
съедают чужих сообщений.

## Диалог принадлежит окну, которое его открыло

```lua
local dialog, err = desktop.dialog({entry = "app.desktop:props", title = "Свойства"})
```

Композитор узнаёт родителя **по отправителю команды**, а не по номеру в
запросе: своего номера окно не знает, а присланный в поле чужой номер ничем не
проверить — так можно было бы объявить своим диалогом любое окно на столе.

Что из связи следует:

| Тип | Поведение |
|---|---|
| `dialog`, `tool` | встаёт по центру своего окна, держится поверх него, закрывается вместе с ним |
| `app` | ничего: программа, открытая из другого окна, живёт своей жизнью |

- **Модальности нет, и это решение, а не недоделка.** Блокировать ввод
  остальных окон там, где окно — чужой процесс под PTY, значит уметь подвесить
  весь стол одной программой, которая не отвечает.
- **`opened_by` записывается всегда**, даже для обычной программы: «кто открыл»
  — это факт, а поведение выбирается типом. Поэтому просмотрщик, открытый из
  «Моего компьютера», не уйдёт вместе с ним.
- **Связь видна снаружи**: `GET /tui-desktop/windows` отдаёт `window_type` и
  `opened_by` на каждом окне. Без этого отладка идёт вслепую: диалог, который
  не закрылся с окном, и диалог, который никогда не был связан, выглядят
  одинаково.
- **Явные координаты сильнее центрирования**: их назвал тот, кто просил.
- **Каскад закрытия живёт в двух местах, и это не дубль.** Вежливое закрытие
  уносит диалоги сразу; второй каскад — на случай окна, умершего само, иначе
  диалог остался бы привязанным к номеру, которого больше нет.

## Вид отделён от механики: контракт темы

Композитор — библиотека `butschster.tui_desktop.desktop:library` с одной
функцией `run(options)`. Всё, что рисуется, приходит темой в `options.chrome`;
геометрию хрома — сколько строк занято сверху и снизу — тоже объявляет она.
Штатная оболочка (`…:desktop`) зовёт `run` со своей темой; вторая оболочка
приносит другую и получает другой вид, не копируя ни хостинг окон, ни PTY,
ни командный канал.

```lua
local library = require("library")
local chrome = require("chrome")

local function main()
    -- Голым `return library.run(...)` это писать нельзя: в go-lua v1.5.18
    -- хвостовой вызов yield-функции из базового фрейма корутины не
    -- выполняется вовсе — молча, за 0 мс.
    local ok, err = library.run({chrome = chrome, service_name = "…"})
    return ok, err
end
```

`options`:

| Поле | Смысл |
|---|---|
| `chrome` | тема. Обязательна: композитор без вида — пустой экран, в котором нечего искать, поэтому отказ называет причину, а не подставляет тему молча |
| `service_name` | имя, под которым композитор виден процессам |
| `hint` | подсказка на пустом рабочем столе |
| `catalog` | `() -> items, failure` — каталог программ. По умолчанию внутренний, плоский |
| `desktop_items` | `() -> items, failure` — раскладка стола: ярлыки и папки. По умолчанию пусто |
| `move_desktop_item` | `(id, x, y) -> ok, error` — записать новое место значка. Композитор раскладку не пишет, а просит: отказ откатывает значок туда, откуда его взяли |
| `restore` | возвращать ли на старте окна мастерской в реестр; по умолчанию да |

Тема — библиотека, возвращающая таблицу. Композитор зовёт только это:

| Функция | Обязана |
|---|---|
| `layout(width, height)` | вернуть `{top = N, bottom = M}` — сколько строк хром забирает сверху и снизу. Рабочий стол — строки `top + 1 .. height - bottom` |
| `fill(canvas, width, height, state)` | залить рабочий стол и нарисовать значки; вернуть разметку попаданий или ничего |
| `window(canvas, window, focused)` | нарисовать рамку, заголовок и содержимое окна |
| `bars(canvas, width, height, state)` | нарисовать полосы (полоса окон, панель задач, статус) и вернуть разметку попаданий |
| `menu(canvas, width, height, items, failure)` | нарисовать каталог программ и вернуть разметку попаданий |
| `empty_desktop(canvas, width, height, text)` | подсказка на пустом столе |
| `BUTTONS`, `BUTTONS_WIDTH` | таблица кнопок заголовка для хит-теста |
| `window_insets()` | толщина рамки: `{top, bottom, left, right}`. По умолчанию единица со всех сторон |
| `icon_grid()` | сетка значков стола: `{w, h, left}` — шаг вправо, шаг вниз, левый край первой колонки |

`state` у `bars` — `{windows, focused_id, menu_open, status, clock}`;
у `fill` — `{top, bottom, items, failure, selected}`.

Окно, которое приезжает в `window(canvas, window, focused)`, несёт
`window_type` — `app`, `dialog` или `tool`, как объявила его запись, — и
`opened_by`, номер окна, из которого его открыли (или `nil`). Состав
кнопок заголовка выбирает по нему тема: композитор только несёт тип от записи
до темы и не знает, во что он превращается. Пункт каталога несёт то же поле,
поэтому тема со своим меню может показывать диалоги иначе, ещё до открытия.

Значки стола: одиночный щелчок выделяет (`state.selected` — id выделенного) и
берёт значок, двойной открывает, отпускание кладёт его по сетке темы.

**Значок без координат ставит композитор**, а не оболочка: ширину экрана
знает только он, а раскладка составляется раньше, чем терминал сообщил
размер. Вычисленное место обратно не записывается — иначе первый же кадр
превратил бы автопосаженный значок в поставленный руками. Отсюда и правило
для оболочки: отсутствие `x`, `y` означает «место никто не называл», а ноль
означает место. Значок, поставленный руками, композитор не двигает никогда,
даже если экран стал уже.
Шаг сетки тема объявляет функцией `icon_grid()` → `{w, h}` (или полями
`ICON_W`, `ICON_H`): она рисует значок и знает, сколько он занимает.
Выравнивает брошенный значок композитор — иначе тот встаёт между шагами и
перекрывается попаданием соседа.

Попадание — запись `{row, from, to, …}` с одним из: `id` (поднять окно),
`index` (пункт меню), `action = "menu"` (открыть или закрыть каталог),
`entry` (открыть программу; на столе — по двойному щелчку).

**Содержимое окна тема обрезает сама.** `canvas:put_rows` держит границу
холста, а не рамки: лишние строки лягут поверх нижней грани и ниже окна.
Обычно их нет — viewport сделан ровно в рамку, — но при смене размера
приезжает кадр прежней геометрии, и на экране это выглядит сломанной рамкой,
а не отставшим кадром.

**Разметка попаданий и отрисовка считаются по одной таблице.** Отдельная
формула для клика однажды разъедется с отрисовкой, и кнопка «закрыть»
окажется на символ левее, чем выглядит. То же про геометрию: пока она была
константой внутри композитора, панель задач снизу требовала правки
композитора — то есть механика снова знала бы про вид.

**Толщину рамки объявляет тема, а не композитор.** Из неё считаются и
размер viewport, который получает программа окна, и смещение курсора, и
наименьший размер окна. Тема с полосой заголовка внутри рамки забирает
сверху три строки; окно, посчитанное по единице, отдало бы программе на
строку больше, чем видно, а окно меньше собственной рамки дало бы viewport
нулевого размера — то есть отказ на открытии, а не кривой вид.

Тема, попросившая больше строк, чем есть на экране, не роняет композитор:
он сводит геометрию к экрану и рисует. Иначе окна уезжают за край молча.

## Окно узнаёт своего композитора при запуске

Имя композитора едет окну в контексте процесса: композитор кладёт его при
`spawn` под ключом `tui_desktop.service`, а библиотека `desktop` читает оттуда.
Раньше имя было константой, и под второй оболочкой окно обращалось к чужому
(несуществующему) процессу — молча, потому что `desktop.open` ответа не ждёт.

- **Ключ один на обе стороны.** Механика берёт его у `window_api`, а не
  повторяет строкой: разойдись они, окно снова взяло бы штатное имя, и вернулся
  бы ровно тот дефект, который здесь починен.
- **Модуль `ctx` объявляет библиотека, а не запись окна.** Библиотека получает
  свои модули, поэтому окна, написанные до этого поля, и окна из мастерской (у
  неё узкий белый список) получают имя без единой правки. Проверено тестом на
  живом запуске, а не выведено.
- **Окно, запущенное без имени, работает как раньше** — берёт штатное
  `butschster.tui_desktop.desktop`.
- **Отказ называет причину и уходит в лог.** «Десктоп такой-то не отвечает;
  имя композитора не пришло при запуске» — во втором возвращаемом значении и
  строкой в логе: `open` ответа не ждёт, и окно, не проверившее возврат, иначе
  не рассказало бы об отказе никак.

## Окно может спросить, не потеряв команду

Вопрос с ответом — `desktop.ask` (ждёт) или `desktop.request` + `desktop.replies()`
(не ждёт). Ответ приходит **своим каналом**, а не в общий inbox, и в этом всё
дело.

```lua
local desktop = require("desktop")

-- окно со своим циклом: канал ответов ложится в select рядом с событиями
local replies = desktop.replies()
desktop.request("desktop.list", {})

-- простой случай: подождать ответ на месте
local answer, err = desktop.ask("desktop.list", {}, {timeout = "2s"})
```

Почему не циклом по inbox, как делает командный канал снаружи: **такой цикл
забирает из inbox всё подряд и выбрасывает то, что не его ответ**, а окну через
тот же inbox приходят чужие сообщения. Измерено на живом запуске: команда
`desktop.close`, посланная окну, пока оно ждало ответ, исчезала без следа —
снаружи это выглядит как окно, переставшее слушаться мышь, и искать будут в
композиторе. Проверка на «ответ пришёл» такую потерю не видит: ответ приходит
в обоих случаях. Поэтому тест проверяет судьбу КОМАНДЫ, и рядом лежит второй,
показывающий тот же сценарий наивным циклом.

Что при этом делает рантайм — тоже измерено, и это важно для читателя:

- **Сообщение, которому некому отдаться, не теряется.** Оно ждёт в очереди
  процесса, пока окно не вернётся к своему `select`. Значит достаточно НЕ
  забирать чужое из inbox; возвращать ничего не нужно, потому что оттуда
  ничего и не взяли. Механика этого — `subs.match(topic)` в
  `runtime/lua/engine/process.go`: сообщение отдаётся подписке на ТОЧНЫЙ топик,
  а inbox — только запасной путь для тех, у кого своей подписки нет; кому
  отдать некому, тот остаётся в очереди. Отсюда общее правило, которым стоит
  мерить такие баги: **теряет пользовательский код, а не рантайм** — искать
  надо цикл, который прочитал и выбросил.
- **События viewport переживают занятое окно.** Клавиши, отправленные окну,
  которое 1.2 с ничего не читало, дошли все и по порядку. Поэтому `ask` не
  теряет ни ввода, ни `close` — но кадр на время ожидания стоит, и срок у
  ожидания есть всегда (`api.BUDGET`, по умолчанию 5 с).
- **Ответ, которого не дождались, выбрасывается перед следующим вопросом.**
  Корреляции у ответов нет, и прочитанный как свежий он ответил бы на прошлый
  вопрос вместо нынешнего. Выбросить ответ безопасно — в отличие от команды.

### Отказ доезжает до того, кто не ждал ответа

`close`, `focus` и `open` ответа не ждут — и всё же узнают об отказе. Композитор
знает отправителя команды, поэтому «нет окна w404» уходит ТРЕМ адресатам, и
каждый нужен своему читателю: строка состояния — человеку за столом, лог — тому,
кто разбирается потом, и сам отправитель — в его канал ответов.

```lua
{ok = false, error = "нет окна w404", command = "desktop.focus", unsolicited = true}
```

- **`unsolicited` обязателен.** Отказ, приехавший сам, встаёт в тот же канал,
  где окно ждёт ответы. Без пометки он был бы принят за ответ на следующий
  вопрос — то есть починка молчания родила бы враньё. `ask` такие сообщения
  пропускает, называя их в логе, и продолжает ждать своё.
- **Каждый ответ называет свою команду** (`command`). Сопоставление по одному
  лишь порядку ломается ровно тогда, когда в поток приходит что-то незваное.
- **Окну, которое канала не создавало**, отказ приходит обычным сообщением в
  inbox — его читает собственный цикл окна.

Окно, которое зовёт `ask` или `replies()`, перестаёт получать `desktop.reply`
в inbox: подписка на топик забирает его себе. Окно, разбиравшее ответы своим
циклом по inbox, менять не обязано — но смешивать оба способа в одном окне
нельзя.

## Устройство

- `src/desktop/programs.lua` — что запись реестра говорит о своей программе: тип окна, признак «показывать в меню». Чистые таблицы, проверяются прямо
- `src/desktop/library.lua` — механика композитора: окна в z-порядке, ввод, команды, отрисовка. Вида не знает
- `src/desktop/desktop.lua` — штатная оболочка: выбор темы и имени, больше ничего
- `src/desktop/chrome.lua` — штатная тема: рамки, заголовки, кнопки, полоса окон; чистые строки без вызовов в рантайм
- `src/desktop/window_pty.lua` — окно: отдаёт свой порт настоящей программе под PTY
- `src/api/` — командный канал, мастерская и их политики
- `src/persist/` — хранилище окон, сборка записи реестра и загрузчик
- `src/migrations/` — таблица окон, собранных в рантайме
- `src/security/` — политики: композитору, каналу, мастерской, окнам, доступу

Права разделены нарочно. Композитору нужно порождать процессы и запускать
программы; командному каналу — только найти композитор и заговорить с ним.
Право `spawn` у ручки означало бы, что HTTP-запрос запускает программы мимо
единственного места, которое их считает.

## Разработка

```bash
make setup     # разрешить зависимости модуля и харнесса
make lint      # wippy lint
make test      # автономный харнесс, реестровые проверки
make verify    # всё вместе
```

Харнесс в `test/` подменяет модуль рабочей копией из `..`, поэтому он же
поднимает десктоп без всякого приложения:

```bash
cd test && wippy run --host butschster.tui_desktop:terminal desktop
```

Полноэкранную программу нельзя проверить кодом возврата: без настоящего
терминала она не запускается вовсе, а запущенная пишет не строки, а поток с
абсолютным позиционированием. Пробник [`tools/tui-probe.py`](tools/tui-probe.py)
даёт PTY заданного размера, печатает по сценарию и разбирает поток в текстовую
сетку — снимок экрана и есть доказательство.

```bash
cd test && python3 ../tools/tui-probe.py --cols 100 --rows 26 --boot 60 \
    --send $'\033n' --send 'echo ok' --send-key enter --expect 'ok' \
    -- wippy run --host butschster.tui_desktop:terminal desktop
```

### Композитор поднимается прямо в тесте

Полтора дня здесь исходили из того, что механику без настоящего терминала не
проверить, и весь класс проверок — z-порядок, фокус, каскад закрытия, resize,
перетаскивание — считался доступным только глазом через пробник. Это неверно.

**Экран композитора не обязан быть терминалом.** `tty.viewport` создаётся прямо
в тестовой функции, `view:grant()` отдаёт его порождаемому процессу — тому же
механизмом, которым композитор раздаёт экраны своим окнам, — и внутри едет
`library.run` со штатной темой. Дальше с ним говорят так же, как командный
канал снаружи, а щелчки едут в его экран настоящими событиями мыши через
`view:send`.

```lua
local view = tty.viewport({width = 80, height = 24})
local pid = process.with_options({terminal = view:grant()})
    :spawn_monitored("app:test_composer", "app:processes", "имя.композитора")
-- ждать не наугад, а появления имени в реестре процессов:
process.registry.lookup("имя.композитора")

view:send({type = "mouse", action = "press", button = "left", x = 4, y = 8})
process.send("имя.композитора", "desktop.list", {reply_to = tostring(process.pid())})
```

Так проверены родство диалога с его окном, поднятие окна щелчком, порядок z,
переход фокуса при закрытии верхнего окна и видимость отказа на команду без
обратного адреса. Живой пример целиком — `test/src/wiring_test.lua` и
`test/src/test_composer.lua`.

Две вещи, без которых это не работает:

- **Ждать надо событие, а не время.** Композитор появляется в реестре
  процессов, когда готов принимать команды, — это и есть сигнал. Готовность
  щелчка проверяется тем же способом: у композитора есть строка состояния,
  которую щелчок по пустому столу очищает, и её исчезновение — веха, по
  которой видно, что событие обработано. Проверки на время врут.
- **Проверка не должна заводить себе способ нажать.** Кнопки открываются
  мышью, потому что мышью их открывает человек; цифровые сокращения в
  интерфейсе, заведённые ради проверки, — это ограничение инструмента,
  протёкшее в продукт.

### Две ловушки, стоившие здесь времени

**Хвостовой вызов.** В go-lua v1.5.18 вызов yield-функции, стоящий последним
как `return f(...)`, не выполняется вовсе — молча, за 0 мс, с пустым
результатом. Такую форму имеют все вызовы этого стека: `tty.start`,
`surface:present`, `viewport:send`, `session:send`. Поэтому они обёрнуты в
`assert(...)`: это не стиль, это обход.

**Экран без размера.** Запуск не из терминала (скрипт, CI, пайп) отвечает на
`screen_size()` нулями, и холст такую ширину отвергает — композитор падал на
первой же строке. Геометрия поэтому проверяется, а не берётся на веру.
